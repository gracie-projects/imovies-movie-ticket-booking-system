## 12. Configure MongoDB

IMovies supports three MongoDB modes, all selected with the single variable `MONGODB_URI`:

| Mode | `MONGODB_URI` value | Use it for | Data kept after restart? |
| --- | --- | --- | --- |
| **In-memory** (default) | `memory` | Development, automated tests, CI | No (auto-seeded on every start) |
| **Local MongoDB** | `mongodb://127.0.0.1:27017/imovies` | Offline development with persistent data | Yes |
| **MongoDB Atlas** (cloud) | `mongodb+srv://<user>:<password>@<cluster>.mongodb.net/imovies?retryWrites=true&w=majority` | Live deployment on Render | Yes |

### Option A: in-memory (no installation)
Nothing to configure. On first start, `mongodb-memory-server` downloads a MongoDB binary once (~600 MB), then starts a private database inside the Node.js process.

### Option B: local MongoDB on Windows
1. Install **MongoDB Community Server** from <https://www.mongodb.com/try/download/community> with the option **Install MongoDB as a Service** selected.
2. Check it's running: open **Services** and find **MongoDB Server** with status *Running*.
3. Set `MONGODB_URI=mongodb://127.0.0.1:27017/imovies` in `backend/.env`.
4. Load the demo data. In `backend/`, run `npm run seed`.

### Option C: MongoDB Atlas (used for the live demo)
1. Create a free **M0** cluster at <https://cloud.mongodb.com>.
2. **Database Access:** create the user `imovies_app` with an autogenerated password and the role *Read and write to any database*.
3. **Network Access:** add `0.0.0.0/0`. Render's free tier has no fixed IP; the database user and password still protect the data.
4. **Connect → Drivers:** copy the connection string, put the password in it, and add the database name `imovies` after `.mongodb.net/`.
5. Paste the string **only** into the hosting provider's environment settings (`MONGODB_URI` on Render) or your local `backend/.env`. **Never commit it to Git.**

The full walkthrough is in [docs/DEPLOYMENT.md](../DEPLOYMENT.md).

## 13. Create Database Connection

File: [backend/src/config/db.js](../../backend/src/config/db.js) (simplified excerpt)

```js
export async function connectDB(uri = env.MONGODB_URI) {
  let target = uri;
  if (uri === 'memory') {
    const { MongoMemoryServer } = await import('mongodb-memory-server');
    memoryServer = await MongoMemoryServer.create();
    target = memoryServer.getUri('imovies');
    logger.warn('Using in-memory MongoDB - data is NOT persisted between restarts');
  }

  mongoose.set('strictQuery', true);
  await mongoose.connect(target, { serverSelectionTimeoutMS: 10000 });
  await Promise.all(Object.values(mongoose.models).map((model) => model.syncIndexes()));
  logger.info({ db: mongoose.connection.name }, 'MongoDB connected');
  return mongoose.connection;
}
```

**How it works**
1. `server.js` calls `connectDB()` **before** the HTTP server starts listening, so the app never accepts requests without a database.
2. With `MONGODB_URI=memory`, a temporary MongoDB is started. `mongodb-memory-server` is imported dynamically, so it's only loaded when needed and isn't required in production.
3. `serverSelectionTimeoutMS: 10000` makes a wrong URI or a blocked IP fail within 10 seconds with a clear error, instead of hanging.
4. `syncIndexes()` creates the unique and query indexes defined in the schemas (for example the unique email and booking reference).
5. `disconnectDB()` closes the connection (and the in-memory server) during graceful shutdown and at the end of tests.
6. `isDbReady()` is used by `GET /api/health/ready`. It returns `503` if the database is disconnected, which Render uses as its health check.

**Production safety:** [config/env.js](../../backend/src/config/env.js) stops the server from starting with `NODE_ENV=production` and `MONGODB_URI=memory`. A public site therefore can't silently lose its bookings.

## 14. Create Schema and Models

All models are in [backend/src/models/](../../backend/src/models). Every schema uses Mongoose validation (`required`, `min`, `max`, `enum`, `match`), `timestamps: true`, and a `toJSON` transform that hides internal fields.

| Model | Important fields | Validation / indexes | Methods |
| --- | --- | --- | --- |
| [User](../../backend/src/models/User.js) | name, email, phone, passwordHash, role | email unique, lowercase, regex-checked; `passwordHash` has `select: false` and is removed from JSON | `setPassword()` (bcrypt hash), `verifyPassword()` |
| [Movie](../../backend/src/models/Movie.js) | title, slug, tagline, description, genres, languages, durationMins, certificate, rating, director, cast, releaseDate, posterUrl, status | slug unique; durationMins 30–300; certificate and status enums; at least 1 genre and language; indexes on title, genres, languages, status | — |
| [Theater](../../backend/src/models/Theater.js) | name, city, address, amenities, isActive | name unique, city indexed | — |
| [Screen](../../backend/src/models/Screen.js) | theater (ref), name, rows, seatsPerRow, premiumRows, aisleAfter | rows 1–26, seatsPerRow 1–30; unique `(theater, name)` | `allSeatIds()` → `["A1", …]`, `seatType(id)`, virtual `capacity` |
| [Showtime](../../backend/src/models/Showtime.js) | movie, theater, screen (refs), startTime, endTime, language, format, prices.standard/premium, bookedSeats, status | format and status enums; indexes `(movie, startTime)`, `(screen, startTime)`, `startTime` | — |
| [Booking](../../backend/src/models/Booking.js) | reference, user, showtime, movie, theater, screen (refs), showStartTime, seats[{id, type, price}], subtotal, convenienceFee, total, paymentMethod, paymentId, status, idempotencyKey | reference unique; **unique `(user, idempotencyKey)`**; at least 1 seat; idempotencyKey hidden from JSON | — |

Example: the Screen schema and its helper methods:

```js
const screenSchema = new mongoose.Schema({
  theater: { type: mongoose.Schema.Types.ObjectId, ref: 'Theater', required: true },
  name: { type: String, required: true, trim: true, maxlength: 40 },
  rows: { type: Number, required: true, min: 1, max: 26 },
  seatsPerRow: { type: Number, required: true, min: 1, max: 30 },
  premiumRows: { type: [String], default: [] },
  aisleAfter: { type: [Number], default: [] },
}, { timestamps: true });

screenSchema.index({ theater: 1, name: 1 }, { unique: true });
screenSchema.methods.seatType = function (seatId) {
  return this.premiumRows.includes(seatId[0]) ? 'premium' : 'standard';
};
```

**Design notes**
- `Booking` keeps a copy of each seat's **price at the time of purchase** and the show start time. Changing showtime prices later never changes what a customer paid, and "upcoming vs past" can be found without a join.
- Showtime `bookedSeats` is the single source of seat availability. Keeping it in one document is what makes the atomic seat reservation possible.
- Relationships use `ObjectId` references plus `.populate()` in queries, for example a booking with its movie title, theater name and screen.

### Seed data ([backend/src/seed/seedData.js](../../backend/src/seed/seedData.js))
`npm run seed` (or automatic seeding on an empty database) loads:
- 2 demo accounts: `demo@imovies.test` (customer) and `admin@imovies.test` (admin).
- 8 fictional movies: 6 now showing and 2 coming soon.
- 2 theaters with 3 screens (8×12, 9×14 IMAX, 7×10 seats).
- 60 showtimes over the next 5 days, at 10:00, 13:30, 17:00 and 20:45 IST.

Seeding refuses to run against a production database unless `--force` is passed and a private `SEED_ADMIN_PASSWORD` is set.
